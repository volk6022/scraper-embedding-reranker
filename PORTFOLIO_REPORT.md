## Контекст и проблема

Разработчики систем информационного поиска и RAG-пайплайнов сталкиваются с одной и той же проблемой: сборка рабочего стека из отдельных инструментов занимает дни. Нужно настроить скрапер с обходом блокировок, развернуть модель эмбеддингов, добавить реранкер для повышения точности выдачи, и сверху — LLM-слой для извлечения структурированного контента из сырого HTML. Каждый компонент требует отдельной конфигурации, управления моделями на GPU, и оркестровки асинхронного взаимодействия между частями.

Без этого сервиса AI-инженер тратит от 2 до 5 рабочих дней на интеграцию Playwright, Hugging Face, PyTorch-инференса и борьбу с VRAM-ограничениями GPU. Параллельно — отдельная задача обхода bot-detection (случайные User-Agent, прокси, имитация человеческого поведения). Все эти задачи рутинны, но трудоёмки.

### Решение

Единый FastAPI-микросервис объединяет четыре специализированных компонента за единым REST API:
1. **Scraper** — запускает headless Chromium через Playwright с ротацией прокси и случайным User-Agent, симулирует поведение пользователя (задержки, прокрутка), рендерит JavaScript и извлекает текст, ссылки, изображения.
2. **Reader** — очищает HTML от мусора (скрипты, стили, SVG, base64-картинки) и с помощью языковой модели jinaai/ReaderLM-v2 преобразует его в структурированный Markdown или JSON.
3. **Embedder** — батчево кодирует тексты в 768-мерные векторы через jinaai/jina-embeddings-v3 с L2-нормализацией для косинусного сходства.
4. **Reranker** — ранжирует документы по релевантности запросу через cross-encoder jinaai/jina-reranker-v2-base-multilingual, возвращая top-N с оценками.

### Измеримый результат

- Скорость интеграции: 4 компонента готовы к использованию с первого запуска вместо 3–5 дней ручной интеграции [NEEDS VERIFICATION]
- Параллелизм скрапера: до 5 конкурентных воркеров по умолчанию, настраивается параметром `max_workers`
- Объём кода: ~800 строк Python production-ready кода в 8 модулях
- Контекст генерации Reader: до 2048 токенов выходного контента за один запрос
- Размерность эмбеддингов: 768 по умолчанию, конфигурируется до 128 для быстрого поиска
- Совместимость API: `/v1/embeddings` и `/v1/rerank` совместимы с форматом OpenAI API
- Мультиязычность: реранкер jina-reranker-v2-base-multilingual поддерживает 100+ языков
- Навигационный таймаут скрапера: 60 секунд с `domcontentloaded` wait strategy

### Языки и фреймворки

| ML-инференс | PyTorch + Hugging Face Transformers | Загрузка и запуск моделей |
| Тензоры | einops + sentencepiece | Манипуляции с тензорами, токенизация |
| Ускорение | accelerate | Оптимизация распределённого инференса |

### Модели

| Модель | Назначение |
|--------|-----------|
| jinaai/ReaderLM-v2 | HTML → Markdown / JSON (causal LM) |
| jinaai/jina-embeddings-v3 | Текст → dense vectors (768-dim) |
| jinaai/jina-reranker-v2-base-multilingual | Query-document relevance scoring |

### Инфраструктура и деплой

Запуск через `python app.py` с CLI-аргументами: `--host`, `--port`, `--lazy-load`, `--low-vram`, `--device`. Сервис готов к контейнеризации (нет жёстких зависимостей от файловой системы). Поддерживает CPU-only окружения — автоматический fallback с CUDA на CPU. Режим `--low-vram` выгружает модели с GPU на CPU между запросами, что позволяет запускать все три ML-модели даже на картах с 8–12 GB VRAM.

### Внешние интеграции

- Hugging Face Hub — автоматическое скачивание весов трёх моделей при первом запуске
- HTTP-прокси — опциональная ротация из `proxies.txt` (формат `http://user:pass@host:port`)
- CUDA — GPU-ускорение инференса при наличии совместимого устройства

```
│Scraper │ │Reader  │ │Embedder  │ │Reranker  │

│Playwright│ReaderLM│jina-emb-v3│jina-rerank│
│+proxies│ │  -v2   │  768-dim  │  v2-multi │
└────────┘ └────────┘ └──────────┘ └──────────┘

```

### Ключевые алгоритмы и паттерны

**Sync-to-Async Bridge**: каждая ML-модель выполняет инференс синхронно (PyTorch не поддерживает native async). Паттерн: `asyncio.Lock` сериализует доступ к модели, `loop.run_in_executor(ThreadPoolExecutor(1))` переносит блокирующий код в поток — FastAPI-сервер при этом остаётся неблокированным.

**[CLS]-токен для эмбеддингов**: вместо mean-pooling используется первый токен (`model_output[0][:, 0]`) как sentence-representation — стандарт для BERT-like моделей с последующей L2-нормализацией.

**Pairwise reranking**: реранкер токенизирует пары `[query] × N + documents` одним батчем, получает N скалярных логитов от sequence classification head, сортирует по убыванию.

**Human-like scraping**: случайные задержки 2–5 с после загрузки страницы, три цикла wheel-scroll с паузами 0.5–1.5 с, viewport 1920×1080. Имитирует поведение реального пользователя, который пролистывает страницу вниз — это также триггерит ленивую загрузку контента (`lazy loading`) на современных сайтах.

**Regex-пайплайн очистки HTML** в Reader: 8 последовательных паттернов (скрипты, стили, meta-теги, HTML-комментарии, link-теги, SVG, base64-изображения, пробельные символы) приводят сырой HTML к виду, пригодному для LLM-обработки без превышения контекстного окна.

### Поток данных

```
URL
 → Scraper → ScrapeResponse { title, content, html, links, images_b64 }
 → Reader  → ReaderResponse { content: markdown/JSON }  (optional)
 → Embedder→ EmbeddingResponse { embeddings: List[float[768]] }
 → Reranker→ RerankResponse { results: [{doc, relevance_score}] }
```

Каждый этап — самостоятельный API-эндпоинт. Клиент сам оркестрирует пайплайн: можно использовать только скрапер, только реранкер, или всю цепочку целиком.

## Бизнес-ценность и целевые клиенты

### Кому это нужно

**AI/ML-инженеры и команды** (стартапы, продуктовые компании), которые строят:
- RAG-системы (Retrieval-Augmented Generation) для корпоративного поиска или чат-ботов
- Пайплайны мониторинга веба (новости, цены, конкуренты)
- Семантические поисковики с учётом релевантности

**Конкретные роли**: ML Engineer, Data Engineer, Backend Developer со специализацией в NLP/LLM.

**Размер бизнеса**: от инди-разработчиков до команд 5–50 человек, не имеющих отдельного DevOps-ресурса для оркестровки ML-инфраструктуры.

### Боль, которую закрывает

Раньше для сборки RAG-пайплайна с веб-источниками нужно было: выбрать и настроить скрапер (Scrapy / Playwright), отдельно развернуть сервис эмбеддингов (self-hosted или через API-провайдера), добавить реранкер для качества выдачи, и сверху — парсер HTML. Каждый компонент — отдельная точка отказа, отдельный сервис, отдельный DevOps-контекст. Этот проект заменяет 4 отдельных сервиса одним контейнером.

### Альтернативы на рынке

| Альтернатива | Проблема |
|-------------|---------|
| Jina AI Cloud API | Платный, данные уходят на сторонний сервис |
| Langchain + отдельные провайдеры | Высокая сложность конфигурации, vendor lock-in |
| Scrapy + отдельный embedding-сервис | Нет единого API, сложнее поддерживать |
| Ручная интеграция | 3–5 дней работы, повторяется в каждом проекте |

Преимущество данного решения — **self-hosted** (данные не покидают сервер), **единый API** (один хост, четыре эндпоинта), **бесплатный инференс** (нет per-token оплаты после развёртывания).

### Потенциальный ROI

Для компании с одним ML-инженером на зарплате 150 000–200 000 ₽/мес: 3–5 дней сэкономленной интеграции = 22 000–45 000 ₽ на первом проекте. При повторном использовании в нескольких проектах — окупаемость с первого применения.

Отказ от облачных embedding API (Jina AI / Cohere) при нагрузке 1M токенов/день — экономия от 15 000 ₽/мес [NEEDS VERIFICATION — зависит от объёмов и тарифного плана провайдера].

Для B2B-сценария (поставка RAG-инфраструктуры клиенту): self-hosted решение без vendor lock-in повышает воспринимаемую ценность предложения — клиент не привязывается к ежемесячным платежам стороннему API-провайдеру. Типичная стоимость аналогичной интеграции как фриланс-проект: 50 000–150 000 ₽ [NEEDS VERIFICATION].

## Ограничения и зоны роста

- **Тесты отсутствуют** — нет unit- и integration-тестов; любой рефакторинг делается вслепую
- **Нет аутентификации** — API открыт без API-ключей или JWT; в production необходим reverse-proxy с auth (nginx / Traefik)
- **Нет rate limiting** — конкурентные запросы к одной ML-модели выстраиваются в очередь за asyncio.Lock, но лимит запросов не ограничен; при нагрузке возможен OOM
- **Нет кэширования эмбеддингов** — одинаковые тексты обрабатываются заново при каждом запросе; Redis-кэш по хэшу текста снизил бы нагрузку на GPU
- **Нет мониторинга** — отсутствует structured logging, метрики (Prometheus), алерты на ошибки инференса
- **Зависимость от GPU-памяти**: три ML-модели суммарно требуют ~10–14 GB VRAM (ReaderLM-v2 — тяжёлая causal LM); без `--low-vram` возможен OOM на картах < 16 GB
- **Ограничения масштабируемости**: single-worker executor на каждую модель означает последовательную обработку запросов; горизонтальное масштабирование возможно только через запуск нескольких экземпляров сервиса за load balancer
- **Прокси-список статичен** — `proxies.txt` читается при запуске; нет API для динамического обновления прокси без рестарта сервиса
